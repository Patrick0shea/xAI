## Purpose of this repository

This repository is an auditable, dated record of how the group's thinking developed over the course of the project — topic selection reasoning, sources considered and rejected, pivots, meeting notes, and drafts-in-progress — culminating in the Report. **It is process evidence, not a second report.**

## Structure

- `journal/` — one dated Markdown file per entry, named `YYYY-MM-DD.md` (e.g. `journal/2026-09-20.md`). See `journal/TEMPLATE.md` for the expected format.
- This `README.md` — stays current with the group's topic, scope, and a link to the latest report draft (see above). Update it whenever those change; don't let it drift.

We're using files under `journal/` as the primary record. GitHub Issues/Projects may be used alongside this for task tracking, but the dated journal entries are the source of truth for traceability.

## Journal conventions

- **Cadence:** at least one substantive entry per week for the duration of the project. A substantive entry documents a decision, a source reviewed, a pivot, or a meeting outcome — not "worked on report today."
- **Each entry should cover:**
  - What was discussed or decided
  - Why (the reasoning, including dead ends and rejected options)
  - What's still open / unresolved
  - Who did what (this matters for individual-contribution tracking)
- **Commit your own work.** Each member commits their own journal entries and contributions rather than having one person transcribe for the group — commit authorship is how individual contribution gets traced.
- **Don't backfill.** Entries should be committed close to when the work happened; a journal written the night before submission defeats the purpose (commit timestamps are checked).

## Traceability to the Report

Where a journal entry leads to a specific section of the Report, link it (e.g. "→ see Report, Section 3: Methodology") so the reasoning trail from journal to final document is easy to follow.
