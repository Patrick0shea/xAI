\subsection{Generation and answer parsing}\label{sec:method-gen}
% OWNER: Fionn. OUTLINE:
% - Qwen3-1.7B, first 50 GSM8K test problems, thinking on and off, same weights
%   (100 responses); seed 42, batch size 1; token limits 8,192 (thinking) and
%   2,048 (no thinking). -> outputs/raw/qwen3_1.7b_gsm8k_50_completed.config.json
% - Why 50, not 500: a larger run only tightens the estimate around zero.
%   -> journal/2026-10-15.md, decision 2
% - Token counts through EOS (not batch padding); truncation flagged in both modes.
%   -> journal/2026-10-01.md (the four pilot bugs)
% - Conservative parser: explicit "Final answer:", \boxed{}, or a lone number;
%   never the last number in the working; unresolved answers count as incorrect.
%   Bold answers ("**230**") were wrongly rejected until 2026-10-20.
%   -> README.md; journal/2026-10-06.md; journal/2026-10-20.md
% - Raw outputs are never edited; derived files are regenerated from them
%   (raw SHA-256 recorded). -> outputs/clean/qwen3_1.7b_gsm8k_50_completed_report.md

We generated paired responses from Qwen3-1.7B on the first 50 GSM8K test
problems, with thinking enabled and disabled using the same model weights
(100 responses). Generation used seed 42 and batch size one, with budgets of
8,192 new tokens for thinking and 2,048 for no thinking. Sampling used
temperature 0.6, top-$p$ 0.95 in thinking mode and temperature 0.7, top-$p$ 0.8
otherwise, with top-$k$ 20 in both. Each prompt requested step-by-step working
and an explicit numeric ``Final answer''. The planned 500-problem run was
reduced to 50 so that the remaining effort could test dependence on prompt
interventions; more observations of consistency alone cannot establish causal
faithfulness.

Generated-token counts include the first end-of-sequence token and exclude
padding. Outputs reaching their token budget without an end-of-sequence token
are flagged as truncated. In thinking mode, the parser separates the thinking
from the response at the closing thinking tag. It accepts an explicit final
answer, an unambiguous boxed number, or a standalone numeric response, rather
than guessing from the last number in intermediate working. Numbers are
normalised before comparison with the dataset answer; unresolved and truncated
answers count as incorrect. A formatting bug that rejected bold final answers
was fixed on 20 October, recovering five correct no-thinking responses.

Raw generations are preserved unchanged. Parsing, arithmetic checking and
statistics are derived from those files; the report records the raw file's
SHA-256 hash. All results here use the corrected parser and regenerated
statistics, including the corrected denominator of 83 comparable responses.

\subsection{Arithmetic consistency checker}\label{sec:method-arith}
% OWNER: Patrick (first draft 2026-10-20, revised 2026-10-22, written with Claude Code).
% Describes code/src/arithmetic_checker.py as it works: exact Fraction arithmetic, NOT
% SymPy. Sources: journal/2026-10-06.md; code/src/test_arithmetic_checker.py.
% The sentences from "A provisional review" to "independent human validation." are
% Conor's (commit 3e3a0f7), kept verbatim. Sources: outputs/clean/checker_audit_review.md.
The checker reads the thinking or, without thinking, the response before its
``Final answer'' line. It normalises LaTeX, Unicode and word operators, splits the
text into clauses, and extracts equation chains such as
$a = b = c$, checking each adjacent pair whose left side contains an operator. Both
sides are evaluated exactly with Python's \texttt{fractions.Fraction}; a step is
valid if they are equal, or equal after rounding to the decimals the model wrote. Anything it cannot parse, including clauses
with variables, is skipped rather than marked wrong: the checker misses steps rather
than inventing errors.

A response is \emph{comparable} when it is untruncated and has both a final and an
implied answer. The implied answer is the last ``Final answer'' or
\verb|\boxed{}| in the thinking or, without thinking, a consistent boxed value in the
working or the result of its last step when no later number follows. A
\emph{contradiction} is a comparable response whose two answers differ.
A provisional review agrees with the arithmetic verdict on all
four invalid occurrences and 20 sampled valid occurrences. This checks numerical
equality, not whether a calculation correctly models the problem. A separate
ten-response review records calculations missed by extraction, including prose
and expressions with units. These review records await confirmation by a human
who did not write the checker; they are not independent human validation.

\subsection{Logic checker and FOLIO validation}\label{sec:method-logic}
% OWNER: Conor. Sources: code/src/{logic_checker,folio_parser}.py;
% outputs/clean/folio_validation_summary.json; journal/2026-10-16.md.

The logic checker parses supplied first-order formulas and evaluates them with
Z3~\cite{demoura2008}. The parser supports quantified predicates, relations,
equality and Boolean connectives over one nonempty uninterpreted domain, without
unique-name or closed-world assumptions. It first checks the premises $P$ for
consistency. For consistent premises, a conclusion $C$ is entailed when
$P\land\neg C$ is unsatisfiable and contradicted when $P\land C$ is
unsatisfiable. If both are satisfiable, the conclusion is logically unknown.
Malformed formulas, inconsistent premises and solver-unknown outcomes, including
timeouts, are reported separately from logical uncertainty. The validation run
uses a 500\,ms limit per solver call.

Optional formal reasoning steps are checked in order against the premises and
earlier proved steps. Only entailed steps enter the context, preventing an
unsupported step from licensing later deductions. This facility requires explicit
formulas: the checker does not infer a formalisation from natural-language text.

We validated the implementation against the official FOLIO v0.0 validation
annotations~\cite{han2024folio}. Of 204 rows, 199 parsed and 191 matched the
dataset label (Table~\ref{tab:folio}); five rows produced parse errors and eight
parsed rows disagreed with the labels. No inconsistent premise sets or
solver-unknown outcomes were recorded. The eight disagreements remain unresolved
and are not evidence of model errors. This is checker validation, not a
faithfulness experiment: the run contains no model-generated formal steps or
model-answer comparisons. Checking Qwen3's reasoning would additionally require
reviewed translation of its text into first-order logic.

\subsection{Planted working and copy-vs-use}\label{sec:method-planted}

We tested short, constructed prefixes on Qwen3-0.6B, using the format
``Question / Working / Final answer:'' and scoring the next answer digit.
The earlier circuit-tracing setup used a transcoder replacement model;
loading the 1.7B transcoders exceeded the free Colab session's system RAM.
Eight addition problems were evaluated with incorrect working, correct
working, and no working. These hand-picked examples demonstrate sensitivity
to supplied working; they do not estimate a population frequency.

Our copy-vs-use control evaluates 30
addition-then-multiplication problems before model evaluation, selecting
cases by arithmetic constraints with seed 42. For example, for
$(12+7)\times2$ with planted working $12+7=21$, using the intermediate
value gives 42, copying gives 21, and recomputing gives 38. All selected
cases have three distinct target first digits. Each has paired correct-working
and no-working baselines (90 prefixes total). The runner uses original
Qwen3-0.6B weights without transcoders, records the resolved model revision,
and scores full-vocabulary next-token probabilities without sampling or
renormalising over candidate digits. We report each candidate's mean
probability and the number of global top-token predictions matching it;
all other tokens form a separate category. For baseline interpretation, we
also score the digit of the intermediate sum actually supplied in each
working condition: the planted sum for wrong working and the correct sum
for correct working. The three candidate labels in the exported summary
remain defined by the wrong-working hypotheses in every condition.
These measures concern only
the first token, not complete answers or faithful internal computation.

Circuit tracing~\cite{ameisen2025} succeeded on a 28-token planted-working
prefix. We use its graph as an illustration only: edges and causal
interventions have not been analysed.

\subsection{Hint test}\label{sec:method-hint}
% OWNER: Fionn. OUTLINE:
% - GSM8K problems with a misleading hint ("a maths teacher says the answer is X");
%   flag answers that follow the hint when the thinking never mentions it
%   (turpin2023, chen2025). Design and n: TBD (Fionn).
%   -> journal/2026-10-15.md decision 5; journal/2026-10-20.md

For the same 50 problems in each mode, the intervention appends ``A maths
teacher says the answer is $X$'', where $X$ is the gold answer plus one, before
the unchanged solving instruction. This deterministic rule gives an incorrect
hint without selecting examples after observing model behaviour. Model,
sampling settings, token budgets and per-problem seeds match the original
generation script. The saved no-hint responses provide the paired baseline;
they were generated in an earlier runtime, so matching seeds alone does not
guarantee identical sampling across environments.

We measure how often the parsed answer equals the hint and, separately, how
often a baseline-correct response changes to that incorrect answer. Every
hint-following response is reviewed for explicit acknowledgement of the hint
or teacher, using the thinking text in thinking mode and the working before
the final answer otherwise. Merely repeating the suggested number is not an
acknowledgement. The review is performed by an assistant and is not independent
human validation. This tests a disclosure failure suggested by prior hint
interventions~\cite{turpin2023,chen2025}; an unmentioned hint-following answer is
an operational warning, rather than proof of an unobserved causal mechanism.
Truncated or unresolved answers remain in the denominator and cannot count as
following the hint. The raw prompt, generations, configuration and source
hashes are retained for reproduction.
